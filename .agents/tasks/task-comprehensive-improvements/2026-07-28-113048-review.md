# Comprehensive Angular SPA refactoring: decomposition, services, accessibility, tests

This change restructures a monolithic Angular 21 e-commerce frontend across 20 distinct improvements. The 521-line `ProductDetailComponent` is decomposed into four child components (gallery, customization, design upload, pricing). Infrastructure is added: a signal-based `ToastService`/`ToastComponent`, a `ConfirmDialogService`/`ConfirmDialogComponent` with focus trap, and a `SkeletonLoaderComponent`. Four static placeholder pages are routed. All native `confirm()` calls are replaced with the dialog service. Unit tests cover `CartService`, `AuthService`, and `ProductService`. Login/Register migrate to signals. Shared components gain `OnPush`. Accessibility additions include skip-to-content, `aria-live` on the cart badge, `prefers-reduced-motion`, focus trap in the mobile menu, and breadcrumb `routerLink` migration.

**Watch for:** The `ConfirmDialogService` leaks its `Subject` if the dialog is opened but the component is destroyed before the user responds (confirmed). The `ProductGalleryComponent` uses a getter with `new Set()` on every change detection cycle, which defeats `OnPush` memoization (confirmed). The `DesignUploadComponent` uses a fake `setTimeout` delay to simulate upload without any cancellation path, meaning rapid re-uploads can race (likely). Test specs rely on mock-mode internals of services rather than testing the public contract through HTTP mocking, which makes them brittle to refactors that swap mock mode out (confirmed).

## High-level view

The product detail decomposition separates concerns into four child components with a smart orchestrator parent. The child components duplicate SCSS class names (`.pd-custom__section` appears identically in both `ProductCustomizationComponent` and `ProductPricingComponent`), and the gallery component's `validImages` getter allocates on every access, defeating `OnPush` memoization.

The confirm-dialog infrastructure has a lifecycle gap: if a subscriber to `ConfirmDialogService.open()` is destroyed before the dialog resolves, the internal `Subject` is never completed and the dialog state stays open on subsequent navigations.

The `CartService` cleanup removes the `LegacyCartItem` interface but `normalizeCartItem` still contains fallback mappings to legacy field names (`r['name']`, `r['thumbnailUrl']`, `r['price']`), leaving the actual migration path incomplete.

The test suites test exclusively through mock mode, validating the mock data pipeline rather than HTTP request/response contracts. They provide signal/state coverage but no regression safety for production code paths.

The four new placeholder pages (help, contact, faq, refund-policy) are all missing `ChangeDetectionStrategy.OnPush` despite being presentational or signal-driven.

## ProductGallery memoization gap

The `ProductGalleryComponent` exposes:

```typescript
get validImages(): string[] {
  const cleaned = normalizeImages(this.images);
  const all = [getSafeImageUrl(this.thumbnailUrl), ...cleaned];
  return [...new Set(all)];
}
```

The template references `validImages` in the `[src]` binding, the `@for` loop, and the `.length` check — at minimum three evaluations per change detection pass. Each creates a new `Set` and array. With `OnPush` this only fires when inputs change, but within a pass the repeated allocation is wasteful. A `computed()` signal derived from an input signal, or caching in `ngOnChanges`, would eliminate redundant work.

## ConfirmDialogService lifecycle gap

The service creates a new `Subject` on each `open()` call and completes it in `close()`. If the subscribing component is destroyed before close (e.g., user navigates away while the dialog is showing), the dialog remains open (`_state.isOpen === true`) and the subject is never completed. The next navigation that renders the `ConfirmDialogComponent` will show a stale dialog.

Fix: inject `Router` in the service and subscribe to `NavigationStart` to auto-cancel, or have `ConfirmDialogComponent.ngOnDestroy()` call `cancel()`.

## Duplicated SCSS across pricing and customization children

Both `product-customization.component.scss` and `product-pricing.component.scss` define identical rules for `.pd-custom__section` (padding, border-bottom), `.pd-custom__section-title` (flex layout, font sizing), and `.pd-custom__step-badge` (circular badge). Angular's view encapsulation means these don't conflict, but a styling change (e.g., adjusting step badge size) must be applied in two places. Extract these shared rules into `src/app/features/public/product-detail/components/_pd-custom-shared.scss` and `@use` it in both.

## CartService: incomplete legacy removal

```typescript
productName: String(r['productName'] ?? r['name'] ?? ''),
productSlug: String(r['productSlug'] ?? r['slug'] ?? ''),
productImage: String(r['productImage'] ?? r['thumbnailUrl'] ?? ''),
unitPrice: Number(r['unitPrice'] ?? r['price'] ?? 0),
```

These fallbacks (`r['name']`, `r['thumbnailUrl']`, `r['price']`) are the exact legacy field names that the removed `LegacyCartItem` interface described. They remain functional — meaning any user with old-format cart data in localStorage will still have it parsed correctly. The task called for removing legacy handling; either strip these and accept a one-time cart reset for affected users, or keep them with an explicit `// MIGRATION: remove after 2025-XX-XX` comment.

## DesignUpload setTimeout race

```typescript
private processArtworkFile(file: File): void {
  this.artworkUploading.set(true);
  setTimeout(() => {
    this.artworkFileName.set(file.name);
    // ...
  }, 800);
}
```

No reference to the timeout is stored. A second call to `processArtworkFile` before 800ms elapses means both callbacks execute sequentially, the first writing stale file data momentarily before the second overwrites. Fix:

```typescript
private uploadTimeout: ReturnType<typeof setTimeout> | null = null;

private processArtworkFile(file: File): void {
  if (this.uploadTimeout) clearTimeout(this.uploadTimeout);
  this.artworkUploading.set(true);
  this.uploadTimeout = setTimeout(() => { /* ... */ }, 800);
}
```

## Test coverage: mock-mode coupling

The `ProductService` spec imports `MOCK_PRODUCTS` and asserts:
```typescript
expect(res.data!.length).toBe(MOCK_PRODUCTS.length);
```

This is a tautology — the service returns `MOCK_PRODUCTS` in mock mode, and the test asserts the count matches. The test can never fail unless `MOCK_PRODUCTS` is modified. Similarly, `AuthService` tests use hardcoded emails (`john.doe@example.com`) that are mock-user fixtures inside the service.

The `CartService` tests are the strongest of the three because they exercise actual state mutations (add, remove, update, clear) and verify signal updates. These have genuine regression value regardless of mock mode.

## Mobile menu focus trap via AfterViewChecked

`AfterViewChecked` fires on every change detection cycle. The component guards with `if (this.isOpen && !this.focusTrapActive)`, preventing redundant listener registration, but the hook overhead remains. Migrating to `ngOnChanges` and checking whether `isOpen` actually changed would be more efficient. In practice, with `OnPush` on the component, `AfterViewChecked` only fires when an input changes, which limits the overhead.
