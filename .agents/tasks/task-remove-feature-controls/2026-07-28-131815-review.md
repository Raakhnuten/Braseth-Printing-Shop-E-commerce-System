# Removal of ProductFeatureControl layer

The entire `ProductFeatureControl` subsystem is excised from the Angular frontend: the interface, mock data, admin CRUD page, service methods, API endpoint constants, and the route. All customization sections (size, color, decoration method, print colors, artwork upload, pricing, production time) are now unconditionally rendered. Validation shifts from "check what the feature control says is enabled" to "check what data is actually available for this product."

Watch for: dead code left behind — four always-true getters in `ProductCustomizationComponent` are unreferenced (confirmed). The `validateDesignUpload` method still accepts a `productId` parameter it no longer uses (confirmed). These are minor but worth cleaning up.

## High-level view

Zero references to `ProductFeatureControl`, the mock data constant, or the three removed service methods survive in `src/`. The admin-layout navigation does not reference the deleted route.

Validation in `ProductDetailComponent` is now data-driven: it requires a selection only when the corresponding option set (sizes, colors, decoration methods) is non-empty. This avoids false-positive errors for products that lack certain options.

The child components (`ProductCustomizationComponent`, `ProductPricingComponent`) retain always-true getter stubs (`enableSizeSelection`, `enablePriceBreak`, etc.) that served as the old conditional gates. The template conditionals that read them were removed, leaving them as dead code.

2. **Dead getters in ProductDetailComponent** — `enableDesignUpload` and `enablePriceBreak` are never referenced in the template after the `@if` guards were removed. Delete them (or inline `isCustomizable` since it too is always `true` and only gates an `if` in `addToCart`).
3. **Unused `productId` parameter in `validateDesignUpload`** — The method no longer looks up per-product config, so the parameter is dead weight. Remove it or mark the intent with a `_productId` convention and a TODO for future API-driven limits.

## Dead getters after conditional removal

`ProductCustomizationComponent` defines four getters that originally drove `@if` guards in its template:

```typescript
get enableSizeSelection(): boolean { return true; }
get enableColorSelection(): boolean { return true; }
get enableDecorationMethod(): boolean { return true; }
get enablePrintColor(): boolean { return true; }
```

The template no longer uses them — the `@if` wrappers around each section were removed. These are orphan symbols. Similarly, `ProductDetailComponent` still exposes `enableDesignUpload` and `enablePriceBreak` getters that no template binding reads.

In `ProductPricingComponent`, `enablePriceBreak` *is* still read by the template (`@if (enablePriceBreak && priceBreaks.length > 0)`) and by `minOrderQuantity`. The indirection through a getter that will always be `true` means the condition could be simplified to just `priceBreaks.length > 0`.

## Unused `productId` in `validateDesignUpload`

```typescript
validateDesignUpload(file: File, productId: string): { valid: boolean; message: string } {
  const maxFileSizeMb = 50;
  const allowedFileTypes = ['image/png', 'image/jpeg', 'image/svg+xml', 'application/pdf'];
  ...
}
```

`productId` is never used inside the method body. It previously drove the mock lookup. Keeping it in the signature is arguably forward-compatible (a future API call might need it), but the method currently never references it. A TODO comment or `_productId` rename would communicate intent.
